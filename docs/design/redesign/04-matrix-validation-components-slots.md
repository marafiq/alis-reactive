# Determinism Matrix — Validation, Components, Slots, Plugins, App-Level Objects

> Source-grounded determinism matrix for the **fresh** redesign. It walks every
> public DSL feature in this band through the **new micro-modules**
> ([`02-micro-modules.md`](./02-micro-modules.md)) using the **new names**
> ([`03-naming.md`](./03-naming.md)), and shows that a deterministic input yields
> exactly one correct output — provably, so code generation is mechanical.
>
> Inputs read from actual source (not inferred): `ReactiveValidator<T>`,
> `ClientValidationFieldRuleBuilder`, `ValidationTerms.cs`, `ComponentObject.cs`,
> `rule-engine.ts`, `orchestrator.ts`, `InputFieldExtensions.cs`,
> `ModelBoundInputComponentSlot.cs`, `InputBoundFieldBase.cs`,
> `InputComponentRegistrationProfile.cs`, the Native/Fusion component slices,
> `ReactivePlugin.cs`, `Builders/PluginTypeBuilder.cs`, `PluginReadBuilder.cs`,
> `PluginContract.cs`, `ReactivePlan.cs` (`RegisterPlugin`:54,66,73),
> `PlanExtensions.cs`, `browser-plans.ts`, `inject.ts`,
> `Builders/PipelineBuilder.cs` (`Into`:273, `ValidationErrors`:263),
> `PlanModel/ReactionGraph.cs` (`InjectReaction`:424, `ShowValidationErrorsReaction`:443),
> `execution/execute.ts` (`executeInject`:207, `executeShowValidationErrors`:220),
> `lifecycle/boot.ts` (`loadPartialSlot`/`unloadPartialSlot`), `PlanTerms.cs`
> (`PlanScope`), and the app-level slices (`NativeDrawer`, `FusionConfirm`,
> `FusionToast`, `NativeLoader`, `NativeActionLink`).

## How to Read a Matrix Row

Each row is one **provably deterministic** unit:

| Column | Meaning |
|---|---|
| **Feature/variant** | The single public capability + the axis it varies on. |
| **Input (DSL)** | The exact C# (or Razor) a developer writes. |
| **Module interaction path** | The ordered new micro-modules and the one thing each does to the data. `→` author side, `⇒` runtime side. |
| **Output** | The exact plan-JSON shape (camelCase, via `PlanSerializer`) **and** the browser behavior it must achieve. |
| **Good default** | The single correct behavior when an optional axis is omitted — chosen so the common case needs no ceremony. |

The point of the matrix: **one deterministic input, walked through the new
micro-modules, yields exactly one correct output.** A row that cannot name a
single output is a non-deterministic hole and is flagged at the end.

### The kernels every row leans on (named once, not repeated)

- **Shape** — `Shape.FromClrType(typeof(TProp))` infers scalar/object/array from
  the CLR property type at authoring; the **shape-once rule** means the value is
  shaped on the gather/compare egress path exactly once; `ShapeConverter` ⇒
  converts at runtime.
- **Kind** — every plan node carries one `kind` string written by
  `PlanNodeDiscriminator` → `PlanSerializer` (camelCase). `PlanContractGenerator`
  reflects the node families into `plan.ts`; `ContractDriftGate` fails the build
  on drift; `assertNever` ⇒ proves the runtime switch is exhaustive.
- **Plan** — `PlanBuildContext` is the authoring sink; `PlanDocument`
  (version=3: `planId`/`scope`/`types`/`components`/`behaviors`) is the immutable
  document; `RenderPlan` serializes it into `<script data-reactive-plan>`; `root`
  ⇒ discovers, `boot` ⇒ wires with `ActivePlan` passed explicitly.
- **Component** — `IdGenerator` produces the deterministic id from the model
  expression; `BrowserObject` (id/vendor/type/role/binding) + `BrowserObjectId`
  `(vendor,kind,id)` + `BrowserObjectContract` (members) are the join keys;
  `RuntimeComponents`/`RuntimeObject` ⇒ resolve via `getElementById` (memoized).

These are stated here once. Rows below name them only where the row's
determinism turns on them.

## Band A — Validation

Validation authoring path (all sync, render-time): `ReactiveValidator<T>` →
`ClientRule(field)` opens a `ClientValidationFieldRuleBuilder` → each rule method
lowers to a `ValidationRuleNode` (renamed from `PlanModel.ValidationRule` to end
the two-`ValidationRule` collision) with one `RuleName`, one `RuleOperand`, an
activation, and a comparison `Shape`. At `RenderPlan` the binder attaches rules
to the container `BrowserObject` (`ValidationGraph`, extracted from the
`ComponentObject` god-file) keyed by the deterministic `IdGenerator` id. Runtime:
`validationOrchestrator` ⇒ reads each component value via `evaluateValue`, runs
`ruleEngine`, reports through `errorDisplay`, and (for `WhenField`) reuses
**Condition's `CompareEngine`**.

The single source of rule names is `RuleName` (18 entries today, generated into
the TS union — replacing the three independent enumerations). The plan-model
operand is one `RuleOperand` with exactly three execution variants:
`none` / `constraint` (literal) / `peer` (reads another field). The runtime
narrows these into 6 wire-evaluation families in `ruleEngine`
(no-operand, length, regex, range, ordered-comparison, equality), each split
literal-vs-peer where applicable — that narrowing is now generated by
`PlanContractGenerator` from the node family, not hand-maintained.

### A1. The 18 rule types (parameterized over `RuleName`)

| Feature/variant | Input (DSL) | Module interaction path | Output (plan-JSON + browser behavior) | Good default |
|---|---|---|---|---|
| **Required** (no-operand) | `ClientRule(m => m.Name).Required("Name is required")` | → `ClientRule` opens `ClientValidationFieldRuleBuilder`; `Required` calls `AddNoOperand(RuleName.Required)`; `RuleOperand.None`; `Shape.None`. → binder attaches a `ValidationRuleNode` to the field's `ValidationGraph` under the container `BrowserObject` keyed by `IdGenerator.For(m=>m.Name)`. ⇒ `validationOrchestrator` reads value via `evaluateValue`, `ruleEngine.requiredFails` = `subject.isEmpty`; `errorDisplay.showInline`. | `{ name:"required", message:"...", execution:{ kind:"none", activation:{kind:"always"}, comparisonShape:{kind:"none"} } }`. Browser: empty field shows the message inline in `{id}_error`; non-empty clears it. | `activation:always`; message required (no implicit text). |
| **Empty / Email / Url / CreditCard / AtLeastOne** (no-operand family) | `.Email("Enter a valid email")` | Same as Required with `RuleName.{Empty\|Email\|Url\|CreditCard\|AtLeastOne}`; `RuleOperand.None`. ⇒ `ruleEngine.{emptyFails\|emailFails\|urlFails\|creditCardFails\|atLeastOneFails}`. | `{ name:"email", ..., execution:{kind:"none", ...} }`. | **MinLength / MaxLength** (length, literal int operand) | `.MinLength(2, "Too short")` | → `AddLiteral(RuleName.MinLength, length, Shape.None)`; guards `length >= 0`; `RuleOperand.Literal(int)`. ⇒ `ruleEngine.lengthRuleFails` compares `subject.length` to constraint; empty passes. | `{ name:"minLength", ..., execution:{ kind:"constraint", value:{kind:"literal", value:2, shape:...}, ... } }`. | **Regex** (literal string operand) | `.Regex("^[A-Z]+$", "Caps only")` | → guards non-empty pattern; `AddLiteral(RuleName.Regex, pattern, Shape.None)`. ⇒ `ruleEngine.regexFails` (invalid pattern fails closed). | `{ name:"regex", ..., execution:{kind:"constraint", value:{literal string}, ...} }`. | **Range / ExclusiveRange** (two literal bounds) | `.Range(1, 10, "1–10")` | → `AddRange` builds `ValidationRangeBounds.FromClientLiteral(lo,hi)`; `RuleOperand.Range(bounds)`; `bounds.Shape` is the comparison shape. ⇒ `ruleEngine.rangeFails` (inclusive vs exclusive). | `{ name:"range", ..., execution:{kind:"constraint", value:{ array of two literals }, comparisonShape:{...} } }`. | **Min / Max / GreaterThanOrEqualTo / LessThanOrEqualTo** (ordered, literal) | `.Min(18, "18+")` | → `AddLiteralComparison(RuleName.Min, value)` via `ClientValidationLiteral.From`; `Gte`/`Lte` alias to `Min`/`Max`. ⇒ `ruleEngine.orderedComparisonFails` (`min`: below fails; `max`: above fails). | `{ name:"min", ..., execution:{kind:"constraint", value:{literal}, comparisonShape} }`. Browser: value below min / above max shows message; empty passes. | `Gte`→`min`, `Lte`→`max` collapse to the same token deterministically. |
| **GreaterThan / LessThan** (ordered, literal, strict) | `.GreaterThan(0, ">0")` | → `AddLiteralComparison(RuleName.Gt\|Lt, value)`. ⇒ `ruleEngine` `gt`: empty OR not-greater fails; `lt`: non-empty not-less fails. | `{ name:"gt", ... }` / `{ name:"lt", ... }`. Browser: strict comparison; note `gt` treats empty as failing (matches source). | Strict tokens distinct from `min`/`max`. |
| **EqualTo / NotEqual** (literal equality) | `.EqualTo("yes", "must be yes")` | → `AddLiteralComparison(RuleName.EqualTo\|NotEqual, value)`. ⇒ `ruleEngine.equalityFails` literal branch. | `{ name:"equalTo"\|"notEqual", ..., execution:{kind:"constraint", ...} }`. Browser: `equalTo` non-equal shows message; `notEqual` non-empty equal-to-forbidden shows message; empty passes. | `comparisonShape` from the literal value. |

**Parameterization.** A1 is 18 `RuleName` tokens × 3 operand-execution variants
(`none`/`constraint`/`peer`). Each token maps to exactly one
`(RuleName, operand-kind, comparisonShape)` triple and one `ruleEngine` arm.
Generation walks the `RuleName` × operand cross-product; the matrix proves the
output is fixed per cell. **18 rule types, fully deterministic.**

#### The 18 `RuleName` tokens → 6 wire-evaluation families (explicit mapping)

The single source of rule names is `ValidationRuleName.Known` — **exactly 18
ordinal-string tokens** (`Alis.Reactive/Validation/ValidationTerms.cs:91-108`,
re-exposed as static accessors at `:118-135`): `required`, `empty`, `minLength`,
`maxLength`, `email`, `regex`, `url`, `creditCard`, `range`, `exclusiveRange`,
`min`, `max`, `gt`, `lt`, `equalTo`, `notEqual`, `notEqualTo`, `atLeastOne`. The
runtime narrows these 18 into **6 evaluation families** — the `switch` arms of
`fieldRuleFails` (`Alis.Reactive.Assets/runtime/validation/rule-engine.ts:57-78`)
and `peerTargetRuleFails` (`:87-99`):

| Wire family (`ruleEngine` arm) | `RuleName` tokens that route here | Operand | rule-engine.ts |
|---|---|---|---|
| **no-operand** (subject-only) | `required`, `empty`, `email`, `url`, `creditCard`, `atLeastOne` | `RuleOperand.None` | `:58,59,63,65,66,78` |
| **length** | `minLength`, `maxLength` | literal `int` | `:60-62` (`lengthRuleFails`) |
| **regex** | `regex` | literal `string` | `:64` (`regexFails`, bad pattern fails closed) |
| **range** | `range`, `exclusiveRange` | two literal bounds | `:72-74` (`rangeFails`, inclusive vs exclusive) |
| **ordered-comparison** | `min`, `max`, `gt`, `lt` | literal **or** peer | `:67-71` literal, `:88-92` peer (`orderedComparisonFails`) |
| **equality** | literal: `equalTo`, `notEqual` · peer: `equalTo`, `notEqualTo` | literal **or** peer | `:75-77` literal, `:97-99` peer (`equalityFails`) |

**Asymmetry to preserve (read from source, not symmetrized):** `notEqual`
(`ValidationTerms.cs:106`) is the **literal-only** token — `NotEqual(TValue,…)`
(`ClientValidationFieldRuleBuilder.cs:108`) — and `notEqualTo`
(`ValidationTerms.cs:107`) is the **peer-only** token — `NotEqualTo(peerField,…)`
(`:111-119`). `equalTo` is the **only** token that carries both a literal overload
(`:95`) and a peer overload (`:98-106`). The runtime mirrors this: the literal arm
matches `equalTo`/`notEqual` (`:75-76`), the peer arm matches `equalTo`/`notEqualTo`
(`:97-98`). A generator must not collapse `notEqual` and `notEqualTo` into one
token. *(This is the validation entry of `06-determinism-confidence.md` Section C —
"`EqualTo`/`NotEqual` literal unconstrained vs constrained peer".)*

> **current vs redesign (determinism).** *current:* the 18→6 narrowing lives only
> in the TS `switch` (`rule-engine.ts:57-99`); the C# side knows only the 18 flat
> tokens, so the C#→TS family grouping is "nowhere in C#" and could drift
> (`06-determinism-confidence.md` Section D). *redesign:* `PlanContractGenerator`
> **derives** the TS union and the family grouping from the C# `RuleName × operand`
> cross-product, and `ContractDriftGate` fails the build on drift — chosen because a
> single generated source for both the 18 tokens and their 6-family grouping makes
> the narrowing mechanical and unforgeable, instead of a hand-kept parallel switch.

## Band B — Components (InputField, Native, Fusion incl. Grid)

Components have one id regime (`IdGenerator`) and one node family
(`BrowserObject` with a `ComponentRole`). The role is the deterministic
discriminator for *what* a component entry is for:

- `plan-input` — a model-bound input rendered by `Html.InputField(...).Xxx()`.
- `object-target` — a non-input object addressed by `p.Component<T>("id")` for
  mutation/read (e.g. a `FusionGrid`, a drawer).
- `validation-container` — the form/container that carries a `ValidationGraph`.
- `layout-object` — an app-level/layout object with a fixed id.

### B1. Input field rendering + registration (the join)

| Feature/variant | Input (DSL) | Module interaction path | Output (plan-JSON + browser behavior) | Good default |
|---|---|---|---|---|
| **InputField + Native input** | `Html.InputField(plan, m => m.Name, o => o.Required().Label("Name")).NativeTextBox(b => b.Placeholder("…"))` | → `InputField` builds a `ModelBoundInputComponentSlot` (`IdGenerator.For(m=>m.Name)`, `BindingPath`, `Shape.FromClrType`). `.NativeTextBox` calls `RegisterInputComponent(NativeTextBox.Registration)` → `InputComponentRegistrationProfile.Register` → `BrowserObject` as `plan-input` with `InputBinding(bindingPath, valueMember:"value")`, `BrowserObjectId(native, textbox, id)`; then `Render` writes the field wrapper (label + `{id}_error`). ⇒ `RuntimeComponents` resolves the input by `getElementById(id)`. | `components[id] = { id, vendor:"native", type:"textbox", role:"plan-input", binding:{kind:"registered-input", bindingPath, valueMember:"value", path:[...]} }` + the input's `BrowserObjectContract` under `types`. **Parameterization.** The framework ships **~60 component slices** — **51 Fusion**
(`Alis.Reactive.Fusion/Components/*`) + **9 Native** (`Alis.Reactive.Native/Components/*`)
+ **4 app-level** (`NativeDrawer`, `NativeLoader`, `FusionConfirm`, `FusionToast`;
Band E). B1 covers the subset that bind a model value — the **input** slices with a
`ValueMember` — parameterized over `{input slice} × {plan-input registration}`. Each
yields exactly one `plan-input` `BrowserObject` whose only per-component deltas are
`vendor`/`type`/`valueMember`/`Shape`. The remaining slices are **display / container
components** (e.g. Breadcrumb, BulletChart, Carousel, ContextMenu, Kanban, ListView,
Menu, PivotView, Schedule, Sidebar, Stepper, Toolbar, Grid, Accordion, Tab, Tooltip,
Dialog) — they have **no `ValueMember`**, so they do not register as `plan-input`;
instead they **reuse the component band's parameterized rows**: their members lower to
`set`/`call`/`read` nodes (B2), their events to `componentEvent` behaviors (B3), and
the largest of them (Grid, B4) proves no display component needs a new plan-node kind.
Generation walks the per-slice member/event list; the node shape is fixed.
**Scales to thousands of fields deterministically because the id is
`IdGenerator`-deterministic and the binding is mechanical.**

## Band C — Partial Slots / Composition

Composition has two axes: **SSR join by `PlanId`** (same-model partials merge
server-side into one plan) and **browser injection by `SlotId`** (load/unload a
partial into a slot, recomposing the active plan). `PlanScope` is the
deterministic discriminator: `root` (SSR-merged) vs `partial` (slot-loadable).

The **only** browser-injection authoring verb is `p.Into(elementId)` — the same
`inject` reaction proven in the Reaction band
([`04-matrix-triggers-reactions-conditions.md`](./04-matrix-triggers-reactions-conditions.md),
`inject` reaction). There is **no `InjectInto` and no `p.Slot(...)` verb in source**;
slot load/unload is a runtime mechanism (`loadPartialSlot` / `unloadPartialSlot` in
`lifecycle/boot.ts`, host-callable) that `injectHtml` invokes automatically based on
whether the injected success HTML carries `<script data-reactive-plan>` elements.

| Feature/variant | Input (DSL) | Module interaction path | Output (plan-JSON + browser behavior) | Good default |
|---|---|---|---|---|
| **Root view plan** | `@{ var plan = Html.ReactivePlan<M>(); } … @Html.RenderPlan(plan)` | → `ReactivePlan` opens `PlanBuildContext` with `PlanScope.Root`; `PlanId` = model `FullName`; `RenderPlan` serializes the `PlanDocument`. ⇒ `root` discovers the `<script data-reactive-plan>`, `composeInitialPlans` joins by `PlanId`, `boot` wires. | `<script id="alis-plan-{sanitized planId}" data-reactive-plan>{ version:3, planId, scope:{kind:"root"}, types, components, behaviors }</script>`. Browser: the plan boots. | One root plan per model per page; id-sanitization is the one shared rule. |
| **Same-model partial (SSR join)** | partial uses `@{ var plan = Html.ResolvePlan<M>(); } … @Html.RenderPlan(plan)` (same `TModel` as the view) | → `ResolvePlan` opens `PlanScope.Partial`; same `PlanId` as the parent. ⇒ at boot, `composeInitialPlans` merges all scripts with the same `planId` (`composeBootPlanInto`: merge `types`, merge `components`, append `behaviors`) into one active `PlanDocument`. | A second `<script>` with the same `planId`; runtime composes into one plan. (`ReactivePlan`/`ResolvePlan`); browser-inject load **and** unload are both driven by
the **one** authoring verb `p.Into(elementId)` — the runtime decides load vs unload
from whether the injected success HTML carries `<script data-reactive-plan>`
elements (`injectHtml`), and the host may also call the runtime `loadPartialSlot` /
`unloadPartialSlot` directly. There is **no** `InjectInto` or `p.Slot(...)` verb in
source. Each combination has one deterministic recompose result because `MergePolicy`
is a single shared replace-vs-append rule and `recompose` always builds a fresh
document. **5 cases, deterministic; the cross-language merge divergence (C# replace
vs TS append) is unified into one `MergePolicy`.**

## Band D — Plugins

A plugin is the typed escape hatch: declare a browser object the DSL does not
model, then read a property / call an operation through the same `Value` and
object-member spines. There are **two** declaration APIs in source — the
`ReactivePlugin` typed-subclass (`ReactivePlugin.cs:13`) and the
`PluginTypeBuilder` stringly-inline builder (`PluginTypeBuilder.cs:11`) — and
**two** ~95%-identical read/call builders. Stringly names are allowed **only** at
the plugin name / member boundary; arguments stay typed.

> **current vs redesign (determinism).** *current:* declaration is split across two
> APIs — the `ReactivePlugin` subclass with **21** `protected` arity overloads
> (`ReactivePlugin.cs:27-132`: `Property<T>` ×1, `Function<TReturn>` member/root ×
> {bare, `Args`, +1, +2, +3 typed args} = 10, `Command` member/root × the same 5 = 10)
> and the `PluginTypeBuilder` with its own parallel `Method`/`Function`/`Property`/
> `Command`/`Void` arity overloads (`PluginTypeBuilder.cs:21-216`) — **~56 arity
> declaration overloads in total** across the two APIs, each a distinct method a
> generator must emit. *redesign:* one `Plugin` declaration surface and one
> `PluginMemberBuilder` args-builder, so the **same** `(member, returns, argShapes)`
> contract is reached by one path — chosen because a single declaration spine makes the
> contract the only thing generation walks, instead of two parallel overload ladders
> that can drift. **The ~56 overloads are an explicit parameterized family
> (`{member,root} × {function,command} × arity 0..3 × {Args}`), not a unified blob:
> each overload is one named cell below, and each lowers to exactly one
> `(member, returns, argShapes)` contract.**

|---|---|---|---|---|

declaration APIs (`ReactivePlugin.cs:27-132` = 21; `PluginTypeBuilder.cs:21-216` =

parameterized family** — `{member-named, root} × {function, command} × arity {0,1,2,3}
× {`Args` escape}` — not collapsed away: each overload is a named cell above and each
lowers to exactly one `(member, returns, argShapes)` `PluginOperationContract`. Three
registration verbs (`RegisterPlugin(ReactivePlugin)`:66, `RegisterPlugin<T>()`:73,
`RegisterPlugin(name, configure)`:54) all land one contract per plugin name.
Generation walks `{registration verb} → members × {declaration overload} × {read,

`(member, returns, argShapes)` triple, which every arity overload reaches identically.**

## Band E — App-Level Objects

App-level objects (Drawer, Loader, Confirm, Toast, ActionLink) are page/application
services with **fixed identifiers**, not model-bound inputs. In the redesign they
are ordinary `BrowserObject`s with `role:"layout-object"` and a fixed id (no
`IdGenerator`, no per-instance wiring) — the same typed-member contract as any
component, never a runtime global. They stay mounted across slot unload.

> **No `p.Drawer()/p.Loader()/p.Toast()/p.Confirm()` verb exists in source — do not invent one.**
> The **only** authoring entry is the **no-arg** `PipelineBuilder.Component<TComponent>()`

> IAppLevelComponent, new()`. It resolves the fixed id from `component.DefaultId`
> (the slice's `ElementId` const) via `ComponentObjectTarget.ForLayout<TComponent>()`
> (`ComponentOnboarding/ComponentObjectTarget.cs:38-45`), which declares a
> `LayoutObjectTarget` (`DeclareLayoutObject`, :77-80). Every member below is a
> `ComponentRef<TComponent,TModel>` **extension method** read from the actual slice —
> there is no special pipeline DSL. Toast's type methods are **parameterless**
> (`.Success()/.Warning()/.Danger()/.Info()`), each an `EmitSet(cssClass, literal)`;
> there is **no** `Show(msg, ToastType, ToastPosition)` signature and the
> `ToastType`/`ToastPosition`/`DrawerPosition` enums are **dead** (zero consumers).

`Component<TComponent>()` overload; each is parameterized over `{object} ×
{ComponentRef extension members}` exactly like Band B (B2 `set`/`call`), with two
fixed deltas: `role:"layout-object"` and a **fixed id constant** (`DefaultId`)
instead of `IdGenerator`. **Current ids are: `alis-drawer`, `alis-loader`,
`alisConfirmDialog`, `alisFusionToast`** — note the Fusion two are camelCase, a
naming inconsistency the redesign should fold into the single-shared-constant rule.
ActionLink is the fifth and differs: it is a render-time element with its own
id generator and an embedded request payload, not an `IAppLevelComponent`.
**5 app-level object families, deterministic; each is a normal `BrowserObject`
(or, for ActionLink, an element + request behavior), never a runtime global.**

> **current vs redesign (determinism).** *current:* the four singleton ids are
> duplicated as a C# `ElementId` const per slice (`NativeDrawer.cs:20`,
> `NativeLoader.cs:18`, `FusionConfirm.cs:12`, `FusionToast.cs:12`) **and** again in
> the TS runtime module, and two of them are camelCase while two are kebab-case
> (`06-determinism-confidence.md` Hole #2). *redesign:* **one shared id constant per
> object** (C# const projected to TS, like `RuleName`) with **one casing
> convention**, so the plan `target` and DOM `getElementById` agree by construction —
> chosen because a single projected constant removes the only place these ids can
> drift.

### Why generation is mechanical for this band

Every row resolves to a **fixed plan-node shape** keyed by one discriminator:
`RuleName`+`execution.kind` (validation), `ComponentRole`+`set/call/read`
(components), `PlanScope`+`MergePolicy` (slots), `plugin member`+`read/call`

registry, or generated-plan validator — the only throws are at genuine boundaries

## Variants I Could NOT Make Fully Deterministic (and why)

These three are **deterministic given a redesign decision**, but the decision is
not yet fixed in source — so I flag them rather than assert a single output.

1. **Validation rule-name set: 18 (C#) vs the runtime's narrowed wire families.**
   `RuleName` lists 18 tokens, but `ruleEngine.ts` narrows them into 6+ evaluation
   families (no-operand, length, regex, range, ordered ×{literal,peer}, equality
   ×{literal,peer}). The mapping is deterministic **only if** `PlanContractGenerator`
   derives the TS union and the narrowing from the C# `RuleName` × operand cross
   product (the redesign's stated intent). Until the generator + `ContractDriftGate`
   exist, the C#→TS narrowing lives "nowhere in C#" and could drift — so the row is
   deterministic *by design* but not *by current source*. Decision needed: confirm
   `PlanContractGenerator` owns the narrowing.

2. **App-level object fixed ids.** Each app-level object's id is a fixed constant
   duplicated between the C# slice (`NativeDrawer.ElementId = "alis-drawer"`, etc.)
   and the TS runtime module. The plan `target` and DOM `getElementById` agree only
   if those constants are unified into **one shared identifier**. The redesign calls
   for this (Band E note), but the shared-constant mechanism is not yet in source, so
   I cannot prove a single id flows end-to-end today. Decision needed: one
   id-constant source per app-level object (C# const projected to TS, like `RuleName`).

3. **`WhenField` activation vs FluentValidation server `When`.** `ReactiveValidator`
   throws (`ReactiveValidator.cs:263-272`, when `_serverOnlyDepth > 0`) if a
   `ClientRule` is declared inside FluentValidation `When/Unless/WhenAsync/UnlessAsync`
   (server-only), and `WhenField` is the client path (rowed in A3 above). This is
   deterministic for the *current* surface, but the boundary between "browser
   activation" (`WhenField` → `ConditionGraph`) and "server-only condition" is enforced
   by a **runtime throw in the authoring API**, not by the type system. To be fully
   deterministic-by-construction the redesign should make "ClientRule under server
   `When`" *unrepresentable* (e.g. a distinct builder surface), matching the
   `Standalone.Then`-becomes-unrepresentable principle. Until then the deterministic
   guarantee rests on a throw, not on an unrepresentable state. Decision needed:
   confirm whether to keep the throw (acceptable authoring boundary) or lift it into
   the type system.

All other 53+ features/variants are deterministic from current source: a single
input walks the named micro-modules to exactly one plan-JSON shape and one browser
behavior.
