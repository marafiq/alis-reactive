# Pre-1.0 Cleanup Spec

**Date:** 2026-04-13
**Base:** `release/1.0.0-preview1` at `df88f154` (post-PR-#108 merge)
**Goal:** Finish the work that CANNOT be done after 1.0 without breaking consumers. Then cut 1.0.

## Scope Principle — Only Irrevocable Work

After 1.0, the following become breaking changes:
- Removing or renaming public API surface
- Changing the JSON wire format
- Demoting `public` to `internal`
- Replacing a nullable property with a sentinel (forces consumers to handle the sentinel)
- Removing a plan model type or schema `$def`

**Everything in this spec is work that must happen BEFORE 1.0 or it's locked out forever.** Anything that can be safely done in `1.1.x` is not in this spec.

## Non-Goals

- **CI Playwright flakes.** They're a known fact of life with Playwright + Syncfusion + Linux Chromium. Local passes, CI flakes 8 specific tests since PR #106 (before my PR existed). Accept them. Triage separately. Not a 1.0 blocker.
- New features
- Performance optimization
- Documentation polish beyond the API contract

## The Work

### P1. Sentinel Cleanup — Lock the Null Model

The null-design-smell branch (PR #108) left ~16 properties nullable. Some are genuinely-absent (locked), some are deferred debt. Once 1.0 ships, converting a nullable property to a sentinel is a breaking change. The window closes at 1.0.

**Tier 1 — Sentinel conversions (structural, clear win)**

1. **Shape discriminated union refactor**

   Currently `Shape` is a single class with nullable sub-properties:
   ```csharp
   public class Shape {
       public string Kind { get; }
       public Shape? Item { get; }     // only valid for kind="array"
       public Shape? Inner { get; }    // only valid for kind="nullable"
       public IReadOnlyDictionary<string, Shape>? Fields { get; }  // only valid for kind="object"
       public bool Additional { get; }
   }
   ```

   Target:
   ```csharp
   public abstract class Shape { public abstract string Kind { get; } }
   public sealed class ScalarShape : Shape { }     // string/number/boolean/date/raw/any/none
   public sealed class ArrayShape : Shape { public Shape Item { get; } }
   public sealed class NullableShape : Shape { public Shape Inner { get; } }
   public sealed class ObjectShape : Shape {
       public IReadOnlyDictionary<string, Shape> Fields { get; }
       public bool Additional { get; }
   }
   ```

   **Impact:**
   - Removes 3 nullable properties (Item, Inner, Fields)
   - Makes illegal shape states unrepresentable by construction
   - JSON schema gains specific `$def` per shape kind (more precise contract)
   - TS types become a proper discriminated union
   - The runtime `shape-convert.ts` / `evaluate.ts` switches become truly exhaustive with `assertNever`

   **Why pre-1.0:** Converting `Shape.Item` from nullable to non-nullable-on-a-subtype is a breaking change to the public plan contract.

2. **NoOpReaction sentinel for `ParallelReaction.OnSettled`**

   Currently `OnSettled` is `Reaction?` with per-property `[JsonIgnore(WhenWritingNull)]`. Add a `NoOpReaction` sealed class (kind="noop"), make `OnSettled` non-nullable defaulting to NoOp. Runtime `executeReaction` switch adds `case "noop": return`.

   **Impact:** -1 nullable, +1 sentinel type, schema/TS/runtime aligned.

   **Why pre-1.0:** Removing the `onSettled?` optionality from the TS type is a breaking change.

**Tier 2 — Explicit "genuinely nullable" lock**

For every property that stays nullable after Tier 1, make a **final binary decision** and commit it in CLAUDE.md as a **locked table**:

| Property | Type | Locked rationale (must be explicit) |
|----------|------|-------------------------------------|
| `Plan.PartId` | `string?` | Only set for partial plans; empty string ≠ absent |
| `Component.BindingPath` | `string?` | Display components have no binding; empty string = "path to root" which is wrong |
| `Component.ValueMember` | `string?` | Display components have no value to read |
| `Component.Container` | `ContainerScope?` | Components outside forms |
| `Request.Container` | `string?` | Requests not scoped to a form |
| `Request.Input` | `RequestInput?` | GET requests have no body |
| `Request.Next` | `Request?` | Recursive — sentinel would create infinite recursion |
| `ResponseHandler.Status` | `int?` | `0` is a valid HTTP status, can't sentinel |
| `DispatchReaction.PayloadType` | `string?` | Empty-string and absent differ in event matching semantics |
| `StartsWhen.PayloadType` (×4) | `string?` | Same — untyped triggers are distinct from "match empty" |
| `PayloadSource.Type` | `string?` | Untyped payloads |
| `JsEvent.PayloadType` | `string?` | Untyped component events |
| `PathSegment.Name` / `Index` | `string?` / `int?` | Discriminated pair — exactly one is set |
| `GatherInput.Statics` | `ValueProducer?` | Not all gathers have statics |
| `GatherInput.IncludeAll` | `bool?` | Uses `WhenWritingDefault` |

This table goes in **CLAUDE.md** as the single source of truth. Any PR trying to add a new nullable property must either fit this table or justify inclusion with file:line evidence that it's semantically distinct from empty.

**Why pre-1.0:** Locking the nullable surface formally means future PRs can be rejected for violating the rule. Post-1.0 it becomes API contract you can't walk back.

### P2. Public API Surface Audit

Every `public` class / method / property in the library projects becomes a 1.0 commitment. Audit:

```bash
rg "^\s*public " Alis.Reactive/ --type cs | grep -v "Interfaces/\|sealed class" | wc -l
# Similar for Fusion, Native, FluentValidator
```

For each, make a binary decision:

- **KEEP public** — intentional part of the consumer-facing API (builder factories, fluent DSL entry points)
- **DEMOTE to internal** — accidentally public; only used inside the framework

Explicit targets for audit:
- Plan model classes (`ValueProducer`, `Condition`, `Shape`, `Reaction`, `Request`, etc.) — their constructors should stay internal (already done), but the classes themselves are public for polymorphism. Verify.
- Builder constructors — should all be `internal`, entry via `Html.*` factories only
- Helper utilities that leaked public from previous refactors

**Output:** a committed list in CLAUDE.md of the 1.0 public surface area, with one-line descriptions.

**Why pre-1.0:** Demoting public to internal is a breaking change. Fixing accidentally-public members is a one-way door that closes at 1.0.

### P3. Wire Format Freeze Test

Add a test to `Alis.Reactive.UnitTests` that captures a canonical plan JSON snapshot of every plan model type. Named:

```
WireFormatIsFrozen_{TypeName}
```

Each test:
1. Constructs a canonical instance via builders
2. Serializes to JSON
3. Asserts the JSON matches a committed snapshot file

If the snapshot changes, the test fails with:

> "Wire format for {TypeName} changed. This is a breaking change to the 1.0 contract. Either revert the change or bump the major version."

**Not** VerifyJson auto-accept. The snapshot files are manually committed after code review. Changing them requires an explicit commit touching the snapshot file, which is visible in every diff.

**Why pre-1.0:** Without this test, any future refactor can silently change the wire format. With it, the test forces the wire format to be an intentional, reviewed commitment.

### P4. Local Linux Playwright (One-Time Validation)

Not a permanent process. A one-time sanity check:

1. Run the full Playwright suite in a Linux Docker container locally (matching CI's ubuntu-latest environment)
2. Document which tests flake (expect the 8 known ones + possibly a few more)
3. If any tests fail that DON'T flake in CI, investigate — they're a real regression

**Why pre-1.0:** Confirms "my local passes, CI flakes" hypothesis. Rules out the scarier hypothesis that there's a framework bug only visible on Linux.

**Why not pre-every-release:** The CI already runs Linux. This is a one-time check to de-risk the 1.0 cut.

### P5. 30-Minute Manual Sandbox Session

Run the Sandbox app locally. Click through 5 scenarios that match real usage:

1. A resident assessment form — fill every field, clear some, refill, submit
2. A medication schedule form — trigger live validation, fix errors, resubmit
3. An HTTP pipeline scenario — GET data, POST it back, handle errors
4. A conditional form — select an option, watch other fields show/hide
5. A multi-partial plan — navigate between views that merge partials

Watch DevTools console throughout. **Zero errors, zero warnings, zero unexpected network calls.**

This is the "would I stake a resident's medication schedule on this today?" test. If you hesitate on any of the 5 scenarios, don't cut 1.0 yet.

**Why pre-1.0:** Synthetic tests cover what we wrote. Manual dogfooding covers what we didn't. 30 minutes catches 80% of integration bugs that tests miss.
