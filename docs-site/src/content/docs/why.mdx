---
title: Why Alis.Reactive?
description: Why the framework uses a generated Reactive Plan instead of view scripts.
---

ASP.NET MVC already gives you strong server-side structure. Models, controllers,
views, validators, and helpers are familiar and testable.

Browser behavior is where that structure often weakens. A view starts with a
small script. Then another script reads a field. Then validation, loading state,
and component refresh code drift away from the C# model.

Alis.Reactive keeps that behavior in the public C# DSL.

You describe what should happen:

```csharp
p.When(args, x => x.Checked).Truthy()
 .Then(t => t.Element("details").Show())
 .Else(e => e.Element("details").Hide());
```

The DSL records that intent into a Reactive Plan. The runtime executes it in the
browser.

## What This Buys You

| Concern | Usual view-script path | Alis.Reactive path |
| --- | --- | --- |
| Event wiring | JavaScript selectors | `.Reactive(plan, evt => evt.Changed, ...)` |
| Payload reads | `event.detail.someValue` strings | `p.When(args, x => x.SomeValue)` |
| Component updates | Vendor object calls in JS | `p.Component<T>(...).SetValue(...)` |
| HTTP payloads | Manually assembled JSON | `.Gather(g => g.IncludeAll())` |
| Client validation | Separate client rule system | `ClientRule(...)` metadata |

The result is not less browser behavior. It is browser behavior with a typed
C# authoring surface.

## What It Is Not

Alis.Reactive is not a SPA framework. Razor still renders the page.

It is not a component catalog. Components are browser objects with events,
properties, and methods. Once you know that shape, native and Syncfusion
components read the same way.

It is not a JavaScript escape hatch. Plugins exist for browser APIs and vendor
features the DSL does not model. Use them at that boundary.
