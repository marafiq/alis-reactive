Reactive is built on one idea: **express intent in C#, carry it as structured data, execute it through the JS runtime.** Three layers, each with a clear boundary.

## Layer 1 — C# Fluent Builders

The developer writes fluent C# in `.cshtml` views. Every call builds a plan model — a data structure that captures what must happen. Nothing executes. The builders are the API surface: triggers, element changes, component calls, conditions, HTTP, and components.

The compiler checks model bindings, event arg types, and response types at build time. Rename a property → compiler error.

## Layer 2 — JSON Plan

`Html.RenderPlan(plan)` serializes all plan models to JSON. This JSON is the **Reactive Plan contract** — the only thing that crosses from C# authoring to the JS runtime. The C# side never executes behavior. The JS side never invents behavior. Both agree on the plan's shape.

The plan is emitted as a `<script type="application/json">` element in the page. It is inert data until the runtime reads it.

## Layer 3 — JS Runtime

An ESM module loaded once via `_Layout.cshtml`. On page load, it discovers all plan elements, parses them, and executes the described behavior. The runtime is a **Reactive Plan interpreter** — it reads structured reactions and applies them through BrowserObject contracts, DOM boundaries, HTTP, validation, and partial slots.

The runtime does not know what a "checkbox" is or what "cascading dropdowns" means. It knows how to set a property, call a method, attach a listener, inject a partial, and make an HTTP request. The Reactive Plan tells it which ones.

Every step in this flow is described in the plan. The runtime follows the instructions. If validation fails, the request never fires. If the server returns 400, the error handler runs. All decided by the plan, not by JavaScript logic.

## The architecture applied everywhere

Every feature follows the same three-layer pattern:

| Feature | C# captures | Plan carries | Runtime executes |
|---------|------------|-------------|-----------------|
| Events | `.Reactive(evt => evt.Changed)` | `startsWhen` + `reaction` | wires listener, runs reaction |
| Element changes | `pipeline.Element("id").Show()` | `set` / `call` reaction | applies the BrowserObject member |
| Components | `pipeline.Component<T>(m => m.Prop)` | component object contract + reaction | resolves root, reads/writes |
| Conditions | `pipeline.When(...).Eq(val)` | branch cases | evaluates, picks branch |
| HTTP | `pipeline.Post(url).Gather(...)` | request + handlers | fetches, routes response |

One idea, five features, zero JavaScript in your views.

## Why this approach?

**Why not Blazor?** Blazor replaces the entire rendering pipeline. Reactive works *with* MVC — same controllers, same Razor views, same model binding. Teams keep their existing investment and add interactivity incrementally.

**Why not generate JavaScript directly?** Generated JS is opaque and hard to inspect. A JSON plan is structured data: generated from the C# domain, compiled into TypeScript types, inspectable in the browser, and the same shape regardless of which C# builder produced it.

**Why not a signals/reactivity library?** Signals solve state propagation. Reactive solves a different problem: expressing server-aware UI behavior (HTTP orchestration, validation, component cascading) without writing JavaScript. The plan carries the full behavior description — the runtime is a dumb interpreter, not a state manager.
