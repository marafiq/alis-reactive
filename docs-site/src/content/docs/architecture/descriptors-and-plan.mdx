Every fluent builder call creates a **plan model**: a plain C# object that describes what must happen without executing it. `ReactivePlan<TModel>` collects those models and renders a JSON **Reactive Plan**. The generated TypeScript contract mirrors the C# plan domain, so the runtime can execute the plan without guessing.

## Behavior — the atomic unit

A `Behavior` pairs a `StartsWhen` trigger with a `ReactionGraph`. The plan is a list of behaviors.

```d2
direction: right

trigger: "StartsWhen\npage-ready | document-event |\ncomponent-event | server-push | signalr" {
  shape: rectangle
  style.fill: "#e8f0fe"
  style.stroke: "#4285f4"
  style.font-size: 18
}
reaction: "ReactionGraph\nsequence | branch | parallel |\nrequest | set | call | dispatch | inject" {
  shape: rectangle
  style.fill: "#fef7e0"
  style.stroke: "#f9ab00"
  style.font-size: 18
}
behavior: "Behavior\nstartsWhen + reaction" {
  shape: rectangle
  style.fill: "#e6f4ea"
  style.stroke: "#34a853"
  style.font-size: 18
}

trigger -> behavior {
  style.stroke: "#4285f4"
}
reaction -> behavior {
  style.stroke: "#f9ab00"
}
```

## Plan model hierarchy

Every discriminated plan node carries a `"kind"` field. The runtime switches on generated union types, not inferred shape.

```text
PlanDocument
├── version
├── planId
├── scope
├── types
├── components
└── behaviors[]
    ├── startsWhen
    │   ├── page-ready
    │   ├── document-event
    │   ├── component-event
    │   ├── server-push
    │   └── signalr
    └── reaction
        ├── sequence                  steps[]
        ├── parallel                  steps[] + completion
        ├── branch                    cases[] (when/default + reaction)
        ├── set                       target + property + value
        ├── call                      target + method + args[]
        ├── request                   RequestPlan
        ├── dispatch                  CustomEvent name + payload
        ├── inject                    slot + HTML value
        └── show-validation-errors    validation container
```

The model is recursive. A branch case can contain a request reaction, a request response route can contain a sequence, and a sequence can contain another branch.

## The plan — collector and serializer

`ReactivePlan<TModel>` has two responsibilities:

**Collecting behavior** — `Html.On()` and component `.Reactive()` calls append behaviors. `Html.InputField()` and component builders register component objects. By the time `Html.RenderPlan(plan)` serializes the plan, it holds every behavior and component registration for the view.

**Serializing to JSON** — `Html.RenderPlan(plan)` emits the complete Reactive Plan JSON:

```d2
direction: right

behaviors: "Behaviors\nstartsWhen + reaction" {
  shape: rectangle
  style.fill: "#e8f0fe"
  style.stroke: "#4285f4"
  style.font-size: 18
}
components: "Components\ncomponent key → object,\nbinding, validation container" {
  shape: rectangle
  style.fill: "#fef7e0"
  style.stroke: "#f9ab00"
  style.font-size: 18
}
types: "Browser object contracts\nproperties, methods,\nevents" {
  shape: rectangle
  style.fill: "#fce8e6"
  style.stroke: "#ea4335"
  style.font-size: 18
}
render: "Html.RenderPlan(plan)\nemits JSON" {
  shape: rectangle
  style.fill: "#e6f4ea"
  style.stroke: "#34a853"
  style.font-size: 18
}

behaviors -> render {
  style.stroke: "#4285f4"
}
components -> render {
  style.stroke: "#f9ab00"
}
types -> render {
  style.stroke: "#ea4335"
}
```

At render time, late-bound pieces are resolved into explicit plan data:

- `IncludeAll()` expands to request input assignments for registered inputs.
- `Validate<T>()` extracts declared client rules from FluentValidation metadata.
- Component references use the registered component key and browser object contract.

## Expression paths — compile-time to runtime

C# expressions like `m => m.Address.City` are walked at build time. Each member path is preserved in the plan as structured path data or as an element/component ID, depending on the DSL call.

| Source | Example expression | Runtime plan role |
|--------|--------------------|-------------------|
| Event payload | `x => x.Address.City` | `PayloadSource` read from trigger payload |
| Response body | `x => x.FullName` | `PayloadSource` read from response route body |
| Component value | `.Value()` | `ComponentSource` read from a plan-registered component |
| Model field | `m => m.Address.City` | component key, DOM ID, validation field binding |

The expression tree gives compile-time type safety. The generated plan gives the runtime a concrete value path.

## Components — the component registry

When `Html.InputField(plan, m => m.Country).FusionDropDownList(...)` runs, the builder registers a component object with its key, role, vendor object contract, input binding, and optional validation container metadata.

The runtime uses component registrations for:

- **Gather** — `IncludeAll()` and explicit gather read registered input values.
- **Validation** — server field names map to component error slots.
- **Execution** — component `set` and `call` reactions resolve the right browser object.
- **Partial composition** — loaded partial slots add and remove component registrations in the Active Plan.

The developer registers once. Every downstream consumer reads from the same plan data.
