Builders narrow context as you compose workflows.

## Builder chain

```d2
direction: right

trigger: "TriggerBuilder\nsubscriptions" { shape: rectangle }
pipeline: "PipelineBuilder\nactions, requests,\nconditions" { shape: rectangle }
element: "ElementBuilder\nhtml.block members" { shape: rectangle }
component: "ComponentRef<T>\ntyped component members" { shape: rectangle }

trigger -> pipeline
pipeline -> element
pipeline -> component
element -> pipeline
component -> pipeline
```

## TriggerBuilder

`Html.On(plan, t => ...)` starts document-level workflow authoring.

It can author subscriptions for:

- dom-ready
- custom events
- server push
- SignalR

## PipelineBuilder

`PipelineBuilder<TModel>` is the main composition surface.

It can author:

- element actions
- component actions
- dispatch
- conditions and branches
- requests and chained requests
- parallel request groups

## ElementBuilder

`Element("id")` targets an HTML block object and produces set/call actions against its declared contract members.

## ComponentRef

`Component<T>(...)` targets a typed runtime object. Extension methods stay vendor-specific, but they emit the same V2 concepts as every other slice.

## HTTP builders

HTTP helpers author request actions with:

- shaped input
- validation
- success/error/settled handlers
- chaining
- parallel branches

## Outcome

The builder chain exists to keep authoring safe and expressive while rendering one runtime model only.
