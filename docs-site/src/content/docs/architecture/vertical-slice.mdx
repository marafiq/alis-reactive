Every component in Reactive is a **vertical slice** — a self-contained set of files that owns everything about that component: its type metadata, events, component reactions, builder, and view integration. No shared base classes for behavior. No cross-slice dependencies.

## The 7-file pattern

Each component follows the same structure. Here's NativeTextBox as a concrete example:

```
NativeTextBox/
├── NativeTextBox.cs                  component class — Vendor + ValueMember
├── NativeTextBoxEvents.cs            event registry — Changed, Focus, Blur
├── Events/
│   └── NativeTextBoxOnChanged.cs     event args — { string? Value }
├── NativeTextBoxExtensions.cs        component reaction extensions — SetValue, FocusIn, Value
├── NativeTextBoxReactiveExtensions.cs .Reactive() wiring
├── NativeTextBoxBuilder.cs           renders HTML, config methods (Placeholder, Type, CssClass)
└── NativeTextBoxHtmlExtensions.cs    Html.InputField().NativeTextBox() factory
```

## What each file does

### 1. Component class — the phantom type

A `sealed class` with a parameterless constructor. Implements `IInputComponent` for model-bound inputs, `IAppLevelComponent` for layout-owned components, or plain `IComponent` for non-input components. Input components declare a `ValueMember`. The type has no runtime state — it exists to constrain extension methods and declare component metadata.

### 2. Events registry — what the component can fire

A singleton class with `TypedEvent<TArgs>` properties. The `.Reactive()` lambda `evt => evt.Changed` resolves to this event definition, which carries the JS event name and the typed args class.

### 3. Event args — typed payload properties

A class with properties like `Value : string?`, `Checked : bool?`, `IsInteracted : bool`. The compiler enforces which properties exist on `args` inside the `.Reactive()` lambda. Filtering args may also have extension methods (`PreventDefault`, `UpdateData`).

### 4. Component reaction extensions — what you can do in the pipeline

Static extension methods on `ComponentRef<TComponent, TModel>`. Each method emits a `SetReaction` or `CallReaction` through `EmitSet()` or `EmitCall()`. `.Value()` returns a `TypedComponentSource<TProp>` for conditions.

### 5. Reactive extensions — wiring events to pipelines

A static extension method on the builder that takes `plan`, an event selector, and a pipeline lambda. Creates a component-event `StartsWhen` node, then adds a `Behavior` to the plan.

### 6. Builder — renders HTML and accepts configuration

Implements `IHtmlContent`. Configuration methods (`Placeholder()`, `CssClass()`, `Items()`) are fluent. `WriteTo()` renders the HTML element. The constructor is internal — devs use the Html factory.

### 7. Html factory — the entry point

Extension method on `InputBoundField<TModel, TProp>`. Creates the builder, calls `setup.RegisterInputComponent(...)`, and calls `setup.Render(builder)` to emit the HTML with label and validation slot.

## Why vertical slices?

**Isolation.** Each slice owns its behavior completely. Adding FusionTimePicker doesn't touch NativeTextBox. Changing NativeCheckBox's events doesn't affect FusionDropDownList.

**Zero runtime changes.** The slice declares vendor, input value member, and BrowserObject members through typed extensions. The runtime already knows how to resolve vendors and execute `set`, `call`, and component-event reactions. No new switch cases, no new component-specific runtime branches.

**Duplication is intentional.** Each slice has its own extensions file, its own reactive extensions, its own builder. The code looks similar across slices — that's by design. Shared abstractions would couple slices and make each one harder to understand in isolation.
