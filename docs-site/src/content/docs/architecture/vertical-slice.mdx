Every component in Reactive is a **vertical slice**: one self-contained unit that owns its authoring metadata, events, actions, builder, and HTML integration. No cross-slice behavior sharing. No runtime branching per component.

## The 7-file pattern

Each component follows the same structure. Here's `NativeTextBox` as a concrete example:

```
NativeTextBox/
├── NativeTextBox.cs                  component class — Vendor + ValueMemberPath
├── NativeTextBoxEvents.cs            event registry — Changed, Focus, Blur
├── Events/
│   └── NativeTextBoxOnChanged.cs     event args — { string? Value }
├── NativeTextBoxExtensions.cs        action/value extensions — SetValue, FocusIn, Value
├── NativeTextBoxReactiveExtensions.cs .Reactive() wiring
├── NativeTextBoxBuilder.cs           renders HTML, config methods (Placeholder, Type, CssClass)
└── NativeTextBoxHtmlExtensions.cs    Html.InputField().NativeTextBox() factory + plan registration
```

## What each file does

### 1. Component class — the phantom type

A `sealed class` with a parameterless constructor. Implements `IInputComponent` (or `IAppLevelComponent`). Declares `Vendor` and `ValueMemberPath`. Has zero runtime state; it exists to constrain extension methods and declare the slice's authoring metadata.

### 2. Events registry — what the component can fire

A singleton class with `ReactiveEvent<TArgs>` properties. The `.Reactive()` lambda `evt => evt.Changed` resolves to one of these typed events, which carries the browser event name and the event payload type.

### 3. Event args — typed payload properties

A class with properties like `Value : string?`, `Checked : bool?`, `IsInteracted : bool`. The compiler enforces which properties exist on `args` inside the `.Reactive()` lambda. Filtering args may also have extension methods such as `PreventDefault` and `UpdateData`.

### 4. Action/value extensions — what you can do in the pipeline

Static extension methods on `ComponentRef<TComponent, TModel>`. Action methods emit member-targeted plan actions. `.Value()` returns a `ComponentValueExpression<TProp>` for conditions, comparisons, and element updates.

### 5. Reactive extensions — wiring events to pipelines

A static extension method on the builder that takes `plan`, an event selector, and a pipeline lambda. It registers a workflow subscription for the rendered component and lowers the event payload contract into the authored V2 plan.

### 6. Builder — renders HTML and accepts configuration

Implements `IHtmlContent`. Configuration methods (`Placeholder()`, `CssClass()`, `Items()`) are fluent. `WriteTo()` renders the HTML element. The constructor is internal — devs use the Html factory.

### 7. Html factory — the entry point

Extension method on `InputBoundField<TModel, TProp>`. Creates the builder, registers the component's metadata with the plan authoring layer, and calls `setup.Render(builder)` to emit the HTML with label and validation slot.

## Why vertical slices?

**Isolation.** Each slice owns its behavior completely. Adding `FusionTimePicker` doesn't touch `NativeTextBox`. Changing `NativeCheckBox` events doesn't affect `FusionDropDownList`.

**Zero runtime changes.** The slice declares vendor, value member path, and events. Authoring lowers those declarations to V2 contracts, objects, bindings, and workflows. The runtime already knows how to execute that model.

**Duplication is intentional.** Each slice has its own extensions file, its own reactive extensions, its own builder. The code looks similar across slices — that is by design. Shared abstractions would couple slices and make each one harder to understand in isolation.
