The runtime is intentionally dumb.

It receives the rendered V2 contract and performs four jobs:

1. merge plans
2. resolve objects and members
3. evaluate values and predicates
4. execute actions

## Runtime modules

- `lifecycle/boot.ts`
- `lifecycle/merge-plan.ts`
- `resolution/contracts.ts`
- `resolution/values.ts`
- `execution/trigger.ts`
- `execution/execute.ts`
- `execution/http.ts`
- `validation/orchestrator.ts`

Each module owns one concern. If behavior leaks across those boundaries, refactor it.

## Subscription wiring

The runtime wires V2 subscriptions:

- `dom-ready`
- `document-event`
- `object-event`
- `server-push`
- `signalr`

The contract already tells the runtime:

- which object is involved
- which event name to use
- which contract member or event payload shape applies

That is why the runtime does not need DOM discovery or vendor guessing.

## Action execution

`execute.ts` dispatches on V2 action kind:

- `sequence`
- `branch`
- `parallel`
- `set`
- `call`
- `dispatch`
- `request`
- `inject`
- `show-validation-errors`

## Request execution

`http.ts` is responsible for:

- input shaping
- validation gating
- `traceparent` propagation
- response routing
- chained requests
- settled handlers

HTTP behavior belongs there, not in views or component slices.

## Tracing

Tracing uses W3C/Otel-style context propagation:

- workflow and action spans are nested
- requests emit client spans
- outgoing requests carry `traceparent`

Tracing should describe real V2 behavior, not recreate deleted abstractions.

## Merge and cleanup

Plan merge is keyed by `planId` and `sourceId`.

Source-owned slices are replaced or removed without scanning the DOM for hidden state.
