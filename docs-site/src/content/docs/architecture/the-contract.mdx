You've seen the fluent C# — `.Reactive()`, `.Post()`, `.When()`. The builders capture intent into a Reactive Plan. This page shows the current generated JSON contract at the level framework developers usually need when changing plan or runtime code.

The authority is the generated TypeScript contract in `Alis.Reactive.Assets/runtime/types/plan.ts`, which is generated from the C# plan domain.

## Top-level structure

Every plan document has the same top-level shape:

```json
{
  "version": 3,
  "planId": "MyApp.Models.ResidentModel",
  "scope": { "kind": "root" },
  "types": { },
  "components": { },
  "behaviors": [ ]
}
```

`planId` is the model's full type name. `scope` identifies root versus partial plan JSON. `types` declares browser object contracts, `components` registers component objects, and `behaviors` is the ordered list of trigger/reaction pairs.

## Behaviors — what starts and what runs

Each behavior has two fields:

```json
{
  "startsWhen": { "kind": "page-ready" },
  "reaction": {
    "kind": "set",
    "on": { "kind": "payload", "scope": "local" },
    "property": "status",
    "value": { "kind": "literal", "value": "ready" }
  }
}
```

`startsWhen` says when the behavior starts. `reaction` is the executable `ReactionGraph` node.

## StartsWhen — what fires

| Kind | Key fields | DSL source |
|------|------------|------------|
| `page-ready` | none | `t.DomReady(...)` |
| `document-event` | `event` | `t.CustomEvent(...)` |
| `component-event` | `component`, `event` | component `.Reactive(...)` |
| `server-push` | `url`, `eventFilter` | `t.ServerPush(...)` |
| `signalr` | `hubUrl`, `method` | `t.SignalR(...)` |

Public DSL names are developer-facing. Wire names are generated plan contract terms.

## Reactions — what happens

The runtime executes a `ReactionGraph`:

| Kind | Purpose |
|------|---------|
| `sequence` | Execute `steps[]` in declaration order. |
| `parallel` | Execute `steps[]` concurrently and optionally run a completion reaction. |
| `branch` | Evaluate `cases[]` and run the first matching reaction. |
| `set` | Assign a property on a component or payload target. |
| `call` | Invoke a method on a component, payload target, or plugin. |
| `request` | Execute an HTTP `RequestPlan`. |
| `dispatch` | Dispatch a `CustomEvent` with optional payload. |
| `inject` | Inject HTML into a partial slot. |
| `show-validation-errors` | Render server validation errors into a validation container. |

There is no separate command layer in the current contract. Element updates, plugin calls, event dispatch, HTTP, and partial injection are all reactions.

## Branches

Branch reactions pair guards with reactions:

```json
{
  "kind": "branch",
  "cases": [
    {
      "guard": {
        "kind": "when",
        "condition": { "kind": "truthy", "left": { "kind": "payload-path", "scope": "event", "path": { "segments": ["checked"] } } }
      },
      "reaction": { "kind": "set", "...": "..." }
    },
    {
      "guard": { "kind": "default" },
      "reaction": { "kind": "set", "...": "..." }
    }
  ]
}
```

The default guard is the `else` case. Conditions stay in the sync lane unless a reached confirm guard crosses the user-decision boundary.

## Requests

HTTP is represented as a request reaction:

```json
{
  "kind": "request",
  "request": {
    "method": "POST",
    "url": "/api/save",
    "validation": { "kind": "container", "container": "intake-form" },
    "input": {
      "kind": "gather",
      "assignments": [],
      "bodyFormat": "json",
      "registeredInputs": { "kind": "all-registered-inputs" }
    },
    "whileLoading": [],
    "success": [],
    "error": [],
    "finally": [],
    "chain": { "kind": "terminal" }
  }
}
```

The request carries method, URL, validation target, gathered input assignments, response routes, final reactions, and optional follow-up request chaining. The runtime follows the generated plan; it does not infer what to post or how to route errors.

## Values — where data comes from

Reactions and request input assignments use `ValueExpression` nodes:

| Family | Examples |
|--------|----------|
| literals | strings, numbers, booleans, null, arrays, objects |
| reads | component properties/methods, plugin properties/methods, URL parameters, payload paths, DOM properties, element methods |
| objects and arrays | structured payloads for dispatch and request bodies |
| array operations | filter, map, count, first, ordering projections |

Shape metadata is generated by the C# plan domain. The runtime applies the declared shape at value-read, validation, condition, and assignment boundaries.

## Components and browser object contracts

`components` registers runtime objects by key. Each component carries a role, object contract, binding metadata, and optional validation container metadata. `types` declares reusable browser object contracts for component and plugin access.

This is why component IDs are absolute join keys: markup, plan JSON, validation, gather, partial composition, and runtime lookup all meet at the same key.

## Why structure matters

Every plan shape is owned by the C# plan domain and mirrored into generated TypeScript. If a builder adds a new `kind` without updating the generated contract and runtime executor, `npm run typecheck` fails before any browser is involved.

| Concept | Valid kinds |
|---------|-------------|
| StartsWhen | `page-ready`, `document-event`, `component-event`, `server-push`, `signalr` |
| Reactions | `sequence`, `parallel`, `branch`, `set`, `call`, `request`, `dispatch`, `inject`, `show-validation-errors` |
| Request input | `none`, `gather` |
| Request targets | `payload`, `header`, `route-param` |
| Response match | `any`, `status` |

If you need a new capability, start in the C# plan domain, regenerate `plan.ts`, and add a focused runtime executor. The generated contract is the gatekeeper. Both sides agree on the shape, and neither reaches beyond it.
