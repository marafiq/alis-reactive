The JSON contract is the only runtime contract.

```json
{
  "version": 2,
  "planId": "MyApp.Models.ResidentModel",
  "sourceId": "resident-form",
  "contracts": {},
  "objects": {},
  "bindings": {},
  "workflows": []
}
```

## Top-level sections

### `contracts`

Capability contracts define readable members, writable members, methods, and events. They isolate vendor-specific access details.

### `objects`

Objects name concrete runtime instances. They bind a contract to a DOM element id or an app-level service object.

### `bindings`

Bindings define the canonical way to read model-facing values from runtime objects.

### `workflows`

A workflow combines a subscription with an action tree.

Subscriptions include:

- `dom-ready`
- `document-event`
- `object-event`
- `server-push`
- `signalr`

Actions include:

- `sequence`
- `branch`
- `parallel`
- `set`
- `call`
- `dispatch`
- `request`
- `inject`
- `show-validation-errors`

## Value expressions and shapes

Value expressions are the read language of the contract. They support:

- literals
- binding reads
- object member reads
- context reads
- object/array construction
- explicit conversion

Shapes define the expected structure:

- scalar
- array
- object
- any

This is how typed C# authoring stays compile-time safe while runtime stays schema-driven.

## Partial merge

`planId` groups related slices.

`sourceId` owns replace/remove behavior for partial content. This is why partial cleanup does not need runtime heuristics.

## Design rule

If a new capability cannot be expressed by extending one of these four sections, it probably does not belong in the framework yet.
