---
title: Reactive Plan
description: The mental model behind the public Alis.Reactive DSL.
---

A Reactive Plan is a typed description of browser behavior.

You author it in C#. `Html.RenderPlan(plan)` serializes it as JSON in the page.
The runtime finds that JSON and executes it in the browser.

## The Shape

```text
Razor view
  -> ReactivePlan<TModel>
  -> triggers
  -> pipelines
  -> JSON plan
  -> browser runtime
```

The C# DSL is the authoring surface. The JSON plan is the contract. The runtime
is the executor.

## The Public Grammar

| Primitive | Purpose |
| --- | --- |
| `Html.ReactivePlan<TModel>()` | Starts a root plan for a view. |
| `Html.ResolvePlan<TModel>()` | Starts a partial plan that merges into the active plan. |
| `Html.RenderPlan(plan)` | Emits the plan JSON. Without this, no behavior runs. |
| `Html.On(plan, t => ...)` | Adds page, custom event, SSE, or SignalR triggers. |
| `Html.InputField(plan, m => m.Field)` | Renders and registers a model-bound input. |
| `.Reactive(plan, evt => evt.Event, ...)` | Adds a component event trigger. |
| `p.Element("id")` | Updates a normal DOM element by ID. |
| `p.Component<TComponent>(...)` | Returns the component; you read, write, and call its members. |
| `p.When(source)` | Branches on a typed value source. |
| `p.Get(...)`, `p.Post(...)`, `p.Put(...)`, `p.Delete(...)` | Adds an async HTTP reaction. |
| `p.Dispatch(...)` | Raises a declared `AppEvent` as a document `CustomEvent`. |

The grammar stays small because components share one object model.

## Components Are Browser Objects

Every component is a JavaScript object with events, properties, and methods. Its
C# class declares them by the names its own API uses, as real C# members, and
`p.Component<T>(...)` returns the component itself.

Events start pipelines:

```csharp
.Reactive(evt => evt.Change, (args, p) => { ... })
```

Properties can be written:

```csharp
var unit = p.Component<FusionDropDownList>(m => m.UnitId);
unit.Value.Set("north-wing");
```

Methods can be called:

```csharp
unit.ShowPopup();
```

Properties, and methods that return a value, are value sources:

```csharp
p.When(unit.Value).Eq("memory-care")
 .Then(t => t.Element("memory-care-note").Show());
```

That pattern is more important than any single component page. A component the
framework does not ship works the same way once its class is declared.

## Values Use One Path

The same value-source idea appears across the DSL.

| Source | Example |
| --- | --- |
| Event payload | `p.When(args.Checked)` |
| Component member | `p.Component<FusionDropDownList>(m => m.UnitId).Value` |
| URL query string | `p.Url<HttpShowcaseQuery>().Get(q => q.ResidentId)` |
| Response body | `body.Get(x => x.Message)`, or `body` itself |
| Plugin return value | `slugify.Slug(planner.Wing)` |

If a DSL primitive needs a value, it should use this shared path.

## Sync and Async

Element updates, component writes, component calls, dispatch, and conditions are
sync reactions.

HTTP, parallel HTTP, confirm decisions, server push, SignalR, and partial
injection are async boundaries.

Keep that distinction in mind when reading a pipeline.

## What To Avoid

Do not add scripts to Razor views for behavior the plan can express.

Do not query the DOM by class or tag to find reactive targets. The plan carries
the IDs the runtime needs.

Do not create a second value resolver. Event payloads, component members, URL
values, response bodies, and plugins all flow through value expressions.
