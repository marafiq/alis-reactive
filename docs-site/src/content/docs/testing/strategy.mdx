Reactive uses separate verification layers because each catches a different
category of bug. `scripts/test.sh` is the full gate; `scripts/test.sh --no-e2e`
is the non-browser gate for changes where browser behavior is intentionally out
of scope.

## What does each layer catch?

### Layer 1 -- Generated Contract + Typecheck

The C# plan domain generates `Alis.Reactive.Assets/runtime/types/plan.ts`.
TypeScript compilation proves the runtime still matches the generated contract.

**Tools:** `npm run typecheck`

The wrapper runs this first so plan-shape drift fails before slower browser work.

**Catches:** Generated type drift after adding new kinds, stale runtime imports,
and C# plan-domain changes that no longer match the TypeScript executor.

### Layer 2 -- TypeScript Unit Tests

The runtime reads a JSON plan and executes it against the DOM. These tests construct a plan object, set up a minimal DOM in jsdom, call `boot()`, and assert the result.

**Tools:** Vitest + jsdom

**Catches:** Reaction handlers writing to the wrong property, path resolution
stopping one level early, JavaScript string coercion mistakes, two-phase boot
regressions (listeners wired after page-ready fires), and guard evaluation
comparing strings when it should compare numbers.

### Layer 3 -- Playwright Tests

The full system running in a real browser. Tests start the SandboxApp on localhost, navigate to pages, interact with components, and assert DOM state and console trace output.

**Tools:** Playwright.NUnit against a live Kestrel server (port 5220)

**Catches:** Integration bugs between C# server and JS runtime, real browser timing and event propagation, Syncfusion component initialization, CSS layout regressions, end-to-end workflows.

---

## Why not just Playwright?

Speed and precision trade off against realism:

| Layer | Speed | Diagnostic precision | Realism |
|-------|-------|---------------------|---------|
| Generated contract | Fastest | Pinpoints plan-shape drift | No runtime |
| TS Unit | Fast (seconds) | Pinpoints exact runtime logic issue | No real browser |
| Playwright | Slowest | Confirms end-to-end, harder to isolate | Full browser stack |

When a Playwright test fails, you know something is wrong but not *where*. Is
the generated plan shape wrong? Is a reaction handler broken? Is a component not
initialized? The lower layers answer that question faster.

## One behavior across the layers

Here is a page-ready dispatch checked across the active layers:

**Generated contract** -- `PlanDocument`, `Behavior`, and `ReactionGraph` stay synchronized:

```bash
npm run typecheck
```

**TS Unit Test** -- runtime executes the dispatch:

```typescript
it("executes a dispatch reaction when document is ready", () => {
  let executed = false;
  document.addEventListener("ready-evt", () => { executed = true; });

  boot({
    version: 3,
    planId: "Test.Model",
    scope: { kind: "root" },
    types: {},
    components: {},
    behaviors: [{
      startsWhen: { kind: "page-ready" },
      reaction: { kind: "dispatch", event: "ready-evt", payload: { kind: "none" } },
    }],
  });

  expect(executed).toBe(true);
});
```

**Playwright Test** -- the class appears in a real browser:

```csharp
[Test]
public async Task all_three_steps_have_green_class_after_chain_completes()
{
    await NavigateTo("/Sandbox/CoreBehaviors/Events");
    await WaitForTraceMessage("booted", 5000);

    await Expect(Page.Locator("#step-1"))
        .ToHaveClassAsync(new Regex("text-green-600"));
    AssertNoConsoleErrors();
}
```

## The rule

Every new primitive (reaction kind, trigger kind, component, validation rule)
needs generated-contract proof, focused runtime proof when runtime behavior
changes, and Playwright proof when browser behavior changes. Before push or
release work, run the full `scripts/test.sh` gate.
